# C2-S11: String.prototype.replaceAll

Status: landed on Mac no-JIT. Unconditional library method. No feature
flag and no kill switch. `String.prototype.matchAll` is not in this batch.
JIT evidence is not claimed; see B4 below.

## Supported configuration

- Default Mac profiles (test and debug-static): `replaceAll` is present.
  `ES6RegExSymbols` and `ES6RegExPrototypeProperties` are off, so
  `@@replace` is not consulted and `RegExp.prototype.flags` is absent.
  A real regexp uses its internal global bit.
- `-ES6RegExSymbols`: after the `IsRegExp` / `flags` check, `@@replace`
  is read only when the search value is an Object. Primitives do not
  consult `String.prototype[@@replace]` or the other primitive
  prototypes. This flag is not the default.
- `-ES6RegExPrototypeProperties`: installs the builtin `flags` getter.
  `replaceAll` then `Get`s it. Not required for the default behavior.
- No kill switch. Removing the method would be a library change, not a
  flag. Precedent: `String.prototype.at`.

## What landed

- Unconditional library method on `String.prototype`, installed with
  `AddFunctionToLibraryObjectWithPropertyName` under a tracked dynamic
  property id. No `builtinFuncs[]` slot, no static `PropertyIds::replaceAll`,
  no bytecode or opcode change, no Backend/JIT helper, and no new `TypeId`.
  `JavascriptBuiltInFunctionList.h` registers
  `BUILTIN(JavascriptString, ReplaceAll, EntryReplaceAll, FunctionInfo::ErrorOnNew)`.
  That is the runtime entry id (`new` throws). It is not an opcode and
  not a bytecode constant. `InitializeStringPrototype` passes `40` to
  `DynamicTypeHandler::Convert` as a property-capacity hint, not as a
  count of own properties.
- Gate and doc files that moved with the two new es7 tests (1962/2014
  was S5; this batch is 1964/2016): `tools/build/check_regression.py`,
  `build.zig`, `.github/workflows/zig-macos.yml`, `doc/memory-management.md`,
  `doc/c1-triage.md`, `doc/modernization-plan.md`. `.gitattributes` gives
  `*.baseline` `whitespace=cr-at-eol` so CRLF snapshot lines are not
  trailing-whitespace errors. Two debugger snapshots list `replaceAll`:
  `test/DebuggerCommon/ES6_proto_invalidation.js.dbg.baseline` and
  `test/DebuggerCommon/TempStrExpr.js.dbg.baseline`.
- Symbols off: `@@replace` is not consulted. After the IsRegExp flags
  check, a real regexp that passed it uses `RegexHelper::RegexReplace` /
  `RegexHelper::RegexReplaceFunction`. A missing `flags` property on a
  real regexp uses the internal global bit. An own or inherited `flags`
  value is `Get`'d. `undefined` or `null` throws `TypeError`
  (`JSERR_NeedObject`). A non-global regexp throws `TypeError`.
- Symbols on: IsRegExp runs first, and only then the flags check, before
  `@@replace` is read. `@@replace` is then read only for an Object search
  value, including a plain object and a regexp whose `@@match` is false.
  A string, number, boolean, or symbol primitive does not read
  `@@replace`. A missing or null `@@replace` on an object falls through
  to the string path, including for a real regexp. A non-callable
  `@@replace` throws `TypeError`. `String.prototype.replace` still reads
  `@@replace` on primitives; that is pre-existing and not part of this
  batch (S7 regexp-symbol cluster).
- An empty search does not use `strstr`. It matches every boundary,
  including both ends.
- The position list is a temp-allocator array released by RAII. The result
  is `CompoundString::Builder::ToString()` before that arena is released.
  The `$` scan in `DoStringReplaceAll` is a third copy of the empty-capture
  scanner already in `RegexHelper::StringReplace` (the helper itself is
  duplicated there). No output divergence was found against the string-path
  cases. Sharing one `GetSubstitution` helper is debt, not this batch.

## Limits

These are platform or pre-existing gaps. They are not open S11 defects.

- Absent `flags`. Spec and Node `Get` `flags` and throw when the result
  is `undefined` or `null`, including after `delete RegExp.prototype.flags`.
  This build, when `flags` is missing on the regexp and its prototype
  chain, uses the internal global bit and does not throw. That is how
  the default profile, which never installs `RegExp.prototype.flags`,
  can still replace every match of `/a/g`. When the property is present
  (own, inherited, or `-ES6RegExPrototypeProperties`), `Get` runs and
  `undefined` / `null` throw.
- Named capture groups are not implemented. A pattern such as
  `(?<named>b)` throws `SyntaxError: Unexpected quantifier` from the
  regexp parser. In the string replacement, `$<name>` stays literal,
  including the `$`. `test/built-ins/RegExp` named-group `replaceAll`
  tests cannot pass on this build. The in-corpus file
  `searchValue-replacer-RegExp-call.js` reaches that pattern only when
  `-ES6RegExSymbols` lets the subclass `@@replace` run.
- `ESBigInt` is off. `cstm-replaceall-on-bigint-primitive.js` fails to
  parse (`Unexpected identifier after numeric literal`). The file is
  tagged `Symbol.replace` and not `BigInt`, so `analyze.py` buckets it
  as `disabled-flag` and a Symbol.replace exclusion hides the parse error.
- `String.prototype.replace` still looks up `@@replace` on primitive
  search values. `replaceAll` does not. The `replace` behavior is
  pre-existing debt.
- `String.prototype.replace` still reports `arguments.length === 1` when
  the replacement is omitted (`CallRegExFunction`). `replaceAll` passes
  an explicit `undefined`, so a custom `@@replace` sees length 2.
- TypeError text differs from Node (`invalid argument` versus a
  non-global RegExp message; `null or not an object` versus null or
  undefined). Tests check the error type only.
- `tools/build/check_regression.py` still feeds `Total: passed 2014`
  into the test expectation as a negative fixture. That line must keep
  rejecting.
- Three regexp-like cases in `test/es7/replaceall.js` return immediately
  when `Symbol.match` or `Symbol.replace` is undefined, so the default
  rlexe launch does not run them. The same cases run from
  `test/es7/replaceall-symbols.js`.

## Ownership

Resource: the match-position array and the copied replacement text,
`AnewArray` on the temp arena inside `DoStringReplaceAll`
(`JavascriptString.cpp`, `ReplaceAllTemp`).

- Domain: `ScriptContext::GetTemporaryAllocator("replaceAll")`, released
  by `ReleaseTemporaryAllocator` in the destructor. Not a GC object.
  Not retained past the call.
- Owner: the stack `ReplaceAllTemp`. Copy and assignment are deleted.
  The builder's `ToString()` runs before the guard ends, so the result
  string is a recycler string and does not borrow the arena.
- Invalidation: destructor on success, on a JS exception from the
  replacer or from `ToString` of a function result, and on unwind.
  A replacer may call `replaceAll` again; each call takes its own
  allocator. Nested depth 8 (past the small temp-allocator cache) and
  a throw from the inner call both leave a later `replaceAll` working.
- User code: the functional replacer and `ToString` of its result.
  Positions are already stored as integers. The `$` scan uses the
  copied `char16` buffer, not a `GetString()` pointer that `Append`
  could flatten.
- Thread: the calling script context only.
- Bound: one array of `matchCount` `CharCount`s plus one copy of the
  replacement. `matchCount` for an empty search is `inputLength + 1`.
  A 4000-match throw at match 50, then a full replacement of that
  input, is the in-tree lifetime test.
- Not claimed: OOM injection, `-RecyclerStress`, or a JIT allocation
  profile. `-RecyclerStress` is a pre-existing mode that corrupts
  untouched builtins.

### Design notes (S11 remainder)

- `Object.groupBy` (`JavascriptObject.cpp`): IsCallable check first
  (before `GetIterator`), then the iterator protocol via file-local
  wrappers (`GroupByGetIterator`, `GroupByCacheIteratorNext`,
  `GroupByIteratorStepAndValue`, `GroupByCallCallback`) in the
  Set-methods style (`JS_REENTRANCY_LOCK`/`JS_REENTRANT` around each
  user-code step). The callback is called with `undefined` this and
  exactly `(value, index)`. The result is
  `library->CreateObject(VarTo<RecyclableObject>(library->GetNull()))`
  — the cached null-prototype type; note a C++ `nullptr` does NOT hit
  that cache and crashes, the null Var does. Each key goes through
  `JavascriptConversion::ToPropertyKey` (so numbers, booleans,
  `-0`→"0", null/undefined, and stringables coerce, and symbol keys
  work), and the group Array is stored as the result object's own
  data property (first-encounter order is the object's insertion
  order). The iterator is closed ONLY at the two spec
  IfAbruptCloseIterator sites — an abrupt `Call(callbackfn, ...)` and
  an abrupt `ToPropertyKey(key)` — and then rethrows the ORIGINAL
  error via `throw JavascriptException(threadContext, exception)`.
  An abrupt `next()` (throwing call, done/value getter, or non-object
  result) is IteratorStepValue's completion, which the spec never
  wraps with IfAbruptCloseIterator, so it propagates WITHOUT closing
  (matching Node 26.5.0); `IteratorStepValue` therefore sits outside
  the close-wrapping try.
- `Map.groupBy` (`JavascriptMap.cpp`): the same walk with the same
  file-local wrappers; keys are NOT coerced, only `-0` is normalized
  to `+0` (mirroring `Map.prototype.set`). The result is
  `library->CreateMap()`, and group lookup/append uses the Map's own
  internal `Has`/`Get`/`Set` (SameValueZero), so no user-visible Map
  method runs on the result. Its single close site is the callback
  call (there is no key coercion); abrupt `next()` shapes propagate
  unclosed exactly as for `Object.groupBy`.
- `RegExp.escape` (`JavascriptRegularExpression.cpp`): a non-String
  argument throws `TypeError` (`JSERR_FunctionArgument_Invalid` with
  the method name) per the final spec — there is no ToString
  coercion. The walk is per CODE POINT over two passes: an exact
  output-length pass and a fill pass into a `BufferStringBuilder`.
  Syntax characters plus `/` are backslash-escaped; U+0009..U+000D use
  the `\t \n \v \f \r` control escapes; the otherPunctuators
  `,-=<>#&!%:;@~'`"` and the WhiteSpace ∪ LineTerminator set (the same
  25-member set as `JavascriptString.cpp`'s `IsWhiteSpaceCharacter`,
  duplicated file-locally as `EscapeIsEsWhitespaceOrLineTerminator`)
  and LONE surrogates become `\xNN` (≤ 0xFF, lowercase) or `\uNNNN`;
  everything else, including a properly paired surrogate, is verbatim.
  The FIRST code point, when it is an ASCII letter or decimal digit,
  is always `\xNN`. Verified exhaustively against Node 26.5.0: all
  65,536 single-BMP-code-unit strings plus pairing and initial-char
  combinations match byte for byte.
- `Promise.try` (`JavascriptPromise.cpp`): IsConstructor(this) first
  (`JSERR_NeedConstructor`), then the callback runs synchronously with
  the forwarded arguments (a `RUNTIME_ARGUMENTS` shift, the
  `Function.prototype.call` idiom) and `undefined` this. A normal
  return goes through `JavascriptPromise::PromiseResolve(C, value)`
  (so an existing promise whose constructor is C is returned
  unwrapped); an abrupt completion goes through
  `CreateRejectedPromise(value, C)` — the spec's `PromiseReject`. A
  NON-CALLABLE callback is a rejected `TypeError`, not a synchronous
  throw, matching `Completion(Call(callback, ...))`. A throw from the
  receiver constructor propagates synchronously (it happens inside
  PromiseResolve/PromiseReject, outside the caught region).
  Divergence note: per that spec PromiseResolve fast path,
  `Promise.try(() => p) === p` holds here — the SAME promise comes
  back and the corpus `built-ins/Promise/try/avoids-wrap.js` (and the
  subclass twin) passes — while Node 26.5.0 wraps and returns a NEW
  promise (`r === p` is false); ch is spec-correct, Node lags.
- `Promise.withResolvers` (`JavascriptPromise.cpp`): IsConstructor(this)
  then `NewPromiseCapability(C)`; the result is
  `library->CreateObject()` with own enumerable `promise`, `resolve`,
  `reject` data properties (`promise` via a tracked dynamic property
  id; `resolve`/`reject` reuse the existing static PropertyIds). The
  capability's functions are the engine's native resolve/reject
  (`name` `""`, `length` 1, one-shot).
- `isWellFormed`/`toWellFormed` (`JavascriptString.cpp`): receiver
  coercion through the shared `GetThisStringArgument`
  (RequireObjectCoercible + ToString). `isWellFormed` is one scan for
  unpaired surrogates; `toWellFormed` scans for the first lone
  surrogate and only then builds a copy (`BufferStringBuilder`),
  replacing each LONE surrogate with U+FFFD and returning the receiver
  itself when the string is already well formed.

## Limits (S11 remainder)

These are platform or pre-existing gaps. They are not open defects in
the seven methods.

- IfAbruptCloseIterator uses the shared
  `JavascriptOperators::IteratorClose`, which swallows a throwing
  `return()`; the original error still propagates. No corpus test in
  the seven directories exercises a throwing `return()`.
- Error message texts differ from Node (`Object.groupBy: argument is
  not a Function object` versus Node's phrasing; `Promise.try` is not
  a constructor` style). The corpus checks error types only.
- `RegExp.escape` throws `TypeError` for a String OBJECT (`new
  String(".")`): the spec's "If string is not a String" is the
  primitive check, and Node 26 matches.
- `ESBigInt` is off; the `1n` receiver case in
  `isWellFormed/toWellFormed` corpus files fails to parse before the
  method runs (`SyntaxError: Unexpected identifier after numeric
  literal`).
- Cross-realm (`RegExp/escape/cross-realm.js`) needs `$262.createRealm()`;
  the harness provides it and both scenarios pass.

## Ownership (S11 remainder)

No new allocation domain. Results are recycler objects
(`CreateObject(null)`, `CreateMap`, `CreateArray`, promise capability
objects, `BufferStringBuilder` strings); the only non-GC scratch is
the `BufferStringBuilder`'s recycler string buffer in `escape` and
`toWellFormed`, sized exactly by the first pass and released by
`ToString()`. No temp arena, no write-barrier change, no retained
stack state. Not claimed: OOM injection, `-RecyclerStress`, or a JIT
allocation profile.

## Review fix (S11 remainder)

Post-review, one verified [risk] finding: the first implementation
wrapped the whole groupBy loop in the close-wrapping catch, so an
abrupt `next()` (throwing call, done or value getter, non-object
result) also closed the iterator. Restructured in
`JavascriptObject.cpp` and `JavascriptMap.cpp`: `IteratorStepValue`
now sits OUTSIDE the close-wrapping try, and only the two spec
IfAbruptCloseIterator sites close — the `Call(callbackfn, ...)`
abrupt (both groupBy) and the `ToPropertyKey(key)` abrupt
(Object.groupBy only) — rethrowing the ORIGINAL error (the
swallowing `IteratorClose` stays spec-correct at those sites).
Abrupt next/value/done propagates unclosed, matching Node 26.5.0
(probes below). `test/es7/s11-builtins.js` gained return-spied
iterator probes for both builtins pinning the no-close shapes, the
close-once shapes, and error identity.
