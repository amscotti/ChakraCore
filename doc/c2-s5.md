# C2-S5: Iterator helpers (implemented and enabled; JIT gated at B4)

Status: closed. Implemented, Mac no-JIT verified, and default-enabled
behind `ESIteratorHelpers` (default `true`), including the review
follow-up (wrap `next` forwards its result unchanged; a
suspended-start `return()` closes in the completed state). This
receipt records the design
decision, the GC/rooting argument required by
[doc/memory-management.md](memory-management.md), the observed
evidence, and every remaining edition-selected failure in scope.
Editorial scope is the ES2025 edition selection of
[doc/c1-triage.md](c1-triage.md) S5: the post-ES2025 `Iterator/concat`,
`zip`, `zipKeyed`, `chunks`, `windows`, `join`, includes/sequencing
and `Symbol.dispose` tests are excluded tags and were not implemented.

## What landed

- The `Iterator` global constructor: abstract (calling it, or
  constructing it with itself as NewTarget, throws `TypeError`),
  subclassable, `length` 0 / `name` `"Iterator"`, its `prototype`
  property is the existing `%IteratorPrototype%` object, and
  GetPrototypeFromConstructor is honoured including the
  NewTarget-realm fallback when `newTarget.prototype` is not an object.
- `Iterator.from(x)` with GetIteratorFlattenable semantics in
  "iterate strings" mode: non-string primitives are rejected, string
  primitives are iterated with the primitive as receiver, iterables go
  through `@@iterator`, a null/undefined `@@iterator` falls back to
  treating the argument itself as an iterator, an iterator that
  already inherits from `%Iterator%` is returned directly, and any
  other iterator is wrapped in a WrapForValidIterator object
  (`%WrapForValidIteratorPrototype%`, whose prototype is
  `Iterator.prototype`). Wrap `next` is a pure forward of the cached
  `next` call: the underlying result is returned unchanged, including
  a non-object result and including calls after a previous `done`
  result, and `done` is not read.
- On `Iterator.prototype` (which *is* `%IteratorPrototype%`): lazy
  `map`, `filter`, `take`, `drop`, `flatMap`; eager `reduce`,
  `toArray`, `forEach`, `some`, `every`, `find`; and the
  `constructor` / `@@toStringTag` accessors whose setters implement
  SetterThatIgnoresPrototypeProperties.
- Iterator Helper objects with `%IteratorHelperPrototype%`
  (`next`/`return`, `@@toStringTag` `"Iterator Helper"`): lazy (no
  underlying pulls before the first `next`), counters start at 0,
  closing happens exactly once (errors, `return()`, take limits and
  eager early exits close; step failures mark that record done without
  calling its `return`; `flatMap` closes inner then outer). Reentrancy
  follows `%IteratorHelperPrototype%.return`: a suspended-start
  `return()` (no `next` yet) sets the generator completed *before*
  `IteratorClose` and does not enter `executing`, so reentrant
  `next`/`return` from that close return a done result. Once the
  helper has started, `return()` and the error-path close run as
  `executing`, and reentrant `next`/`return` throw `TypeError`
  (Node returns a done result on this started path; the spec's
  `GeneratorValidate` throws). Brand checks reject plain
  objects, generators and wrap objects (and generator `next`
  rejects helpers).
- Validation order follows the tests: `this` object check first, then
  callable/limit validation against a placeholder record that closes
  the underlying iterator (reading/calling `return` only, never
  `next`) on failure, and only then GetIteratorDirect caches `next`
  exactly once. Limit conversion is ToNumber; NaN, a finite value
  above 2^53-1, or a truncated value below 0 is a `RangeError`;
  finite values truncate toward zero and `Infinity` is allowed. (The
  S5 task summary said "NaN -> 0"; the current test262 tests encode
  NaN as `RangeError`, and the tests were followed.)

## Design decision: pure C++ helper objects

Three paths were investigated before writing code.

1. **JS-implemented builtins** (`InJavascript/*.js` plus
   `regenByteCode.py` bytecode regeneration). Rejected. The JsBuiltIn
   registration mechanism can only attach functions to pre-existing
   library objects, so the `Iterator` constructor, the helper and
   wrap prototypes, and helper object creation would still need C++;
   the lazy helpers would then be split across two languages for no
   gain, and every bytecode header would need regeneration.
2. **Generator-backed helpers** (a JS generator per helper, in the
   shape of the spec's CreateIteratorFromClosure). Rejected on brand
   and prototype identity: a real generator object's prototype is its
   generator function's prototype, not the single shared
   `%IteratorHelperPrototype%`, and swapping the prototype would make
   `%IteratorHelperPrototype%.next` shadow the generator machinery.
   Generator brand checks would also accept helpers where the spec
   (and the staging tests) require `TypeError`.
3. **A dedicated C++ object** — chosen. `JavascriptIteratorHelper`
   (in the existing `JavascriptIterator.h/.cpp`, so no build-system
   source lists change) is a `DynamicObject` subclass carrying the
   underlying Iterator Record, the callback, flatMap's inner record,
   the counter/remaining doubles, and `completed`/`executing` state
   mirroring the generator brand's executing check. Helper and
   WrapForValidIterator objects share the class and one reclaimed
   TypeId (69, the long-deleted VariantDate slot, so no existing
   TypeId moves), distinguished by a `kind` field; brand checks are
   TypeId-plus-kind, which is realm-independent.

The closest registration sibling is `%TypedArray%`
(`CreateBuiltinConstructor` + deferred constructor initializer +
prototype object created in `InitializePrototypes`); the closest
traced-object sibling is `JavascriptAsyncFromSyncIterator` (see the
GC argument below). New `take`/`drop`/`toArray`/`Iterator` property
names use tracked dynamic property ids
(`GetOrAddPropertyIdTracked` /
`AddFunctionToLibraryObjectWithPropertyName`, the telemetry-global
precedent) instead of new `JnDirectFields.h` entries, so built-in
bytecode is byte-unchanged — the `zig build check` and debug-static
`verify-bytecode` steps both still print `Bytecode is up to date`.

## GC / rooting argument (memory-management record)

| Aspect | Record |
| --- | --- |
| Allocation domain | ScriptContext Recycler of the creating library (`RecyclerNew` in `JavascriptLibrary::CreateIteratorHelper` / `CreateWrapForValidIterator`); no host, arena, or script-agnostic allocation is introduced. |
| Owner / retained pointers | The helper object owns `Field(RecyclableObject*)` underlying (and inner) iterators and `Field(Var)` cached `next` methods and callback, exactly the `JavascriptAsyncFromSyncIterator` Field() pattern. There is no custom tracer: `DEFINE_VTABLE_CTOR` plus `RecyclerNew` makes the object a ScriptContext-recycler object, and on non-Windows builds `GLOBAL_ENABLE_WRITE_BARRIER` is 1, so those pointer `Field`s are `WriteBarrierPtr`s the recycler rescans. Bool and double fields are not barrier pointers. Nothing is stored in native containers or untraced structs. |
| Transfer / invalidation | Records are created on the C++ stack by GetIteratorDirect/GetIteratorFlattenable and transferred into the helper's fields at construction (barrier stores in the constructor). The only post-construction pointer stores are `innerIterator` and `innerNextMethod` in `Advance` (flatMap); those assignments go through `WriteBarrierPtr::operator=`, so a concurrent marker sees the new edges. `[[Done]]` flags are set before any user `return` is called. Suspended-start `return()` sets `completed` and does not set `executing` before closing. A started `return()`, and the error-path close inside `next()`, set `executing` so reentry throws. A record is closed at most once either way. |
| Completion / exceptions | User-code exceptions are caught, the helper is marked completed, still-open records are closed with throw-completion semantics (close errors swallowed), `executing` is cleared, and the original exception object is rethrown via `DoThrowCheckClone`. Cache invalidation is per-record (`done`), never by dropping fields. |
| Thread / context | Helpers are created and used on the owning ScriptContext's thread; cross-context use goes through the ordinary marshalling path (`DEFINE_MARSHAL_OBJECT_TO_SCRIPT_CONTEXT`, as for `JavascriptArrayIterator`), and brand checks key on TypeId/kind, not on the calling realm's prototype object. |
| Accounting | No external/native memory is allocated; nothing to report to JsRT memory accounting. Each helper and each wrap calls `DynamicType::New` (same shape as `CreateAsyncFromSyncIterator`). That is one type per instance, which is an inline-cache / type-growth cost to measure at B4 before any shared-type change. |

Observed GC evidence: a probe whose underlying iterator, `vals`
array and mapper closure are reachable *only* through a
`map`/`flatMap` helper chain (and a wrap object whose plain iterator
is likewise unreachable) survives 4M throwaway object allocations
between pulls and produces the full correct sequence, on the Test
binary.

## Review follow-up

Checked against ECMA-262 2025 `%WrapForValidIteratorPrototype%.next`,
`%IteratorHelperPrototype%.return`, and `GetIteratorFlattenable`, and
against Node 22.22.3 for the same scripts.

- Wrap `next` previously required an object result and read `done`
  (`IteratorComplete`). Both are gone. The in-tree test covers a
  `done` getter that must not run, and a non-object result (`5`)
  that must be returned unchanged.
- Fresh-helper `return()` previously set `executing` before closing,
  so reentrant `next`/`return` threw. It now sets `completed` only.
  The started path (after `next()`, and the mapper-throw close)
  still throws. The in-tree test covers both directions. Node agrees
  on the fresh helper and returns a done result on the started path;
  the started `TypeError` is the spec.
- Deleting `String.prototype[@@iterator]` does **not** wrap the
  string. The ES2025 algorithm sets the iterator to that primitive
  and then throws because it is not an Object (step 5). This engine
  throws `TypeError` (`JSERR_NeedFunction`) as soon as the string's
  `@@iterator` is missing or not callable, which is the same
  outcome. Node 22 throws `TypeError` as well (`ab is not
  iterable`). The in-tree test locks the throw. No engine change.
- `git diff --check` trailing blank line at the end of
  `JavascriptIterator.cpp` is removed. `test/es7/iteratorhelpers.js`
  has the ChakraCore Project Contributors copyright line.
  `doc/memory-management.md` cites the 1962-case baseline.
- The "~4,000 fuzzed chains under forced exhaustive GC" figure is
  not evidence in this receipt and has no stored artifact.
  `-RecyclerStress` is a pre-existing mode that corrupts untouched
  builtins, so it is not a liveness proof. The liveness note above
  is the normal-GC allocation probe only; this follow-up did not
  re-run it.
- `test/es7/iteratorhelpers.js` does not skip when
  `-ESIteratorHelpers-` leaves `Iterator` undefined (the file is
  still in `rlexe.xml`). The default suite does not pass that
  switch. Left as debt.

## Unresolved / deferred

- **JIT (B4 gate):** all evidence here is Mac no-JIT. The feature is
  ordinary runtime-library code reached through runtime calls (no
  new opcodes, no JIT inlining of the helpers), but per the plan's
  standard matrix, B4 must still run the S5 test262 corpus and the
  es7 test under SimpleJIT/FullJIT before any JIT-configuration
  claim. Kill switch: `-ESIteratorHelpers-`. Before that claim, also
  check: inline-cache and type growth from per-instance
  `DynamicType::New`; JIT paths that switch on `TypeIds_IteratorHelper`
  (69, the reclaimed VariantDate slot) including `IsJsNativeType` and
  the JsRT debug type switch; property lookup of the tracked dynamic
  ids `take` / `drop` / `toArray` (they are not bytecode constant
  slots); cross-realm marshalling (`DEFINE_MARSHAL_OBJECT_TO_SCRIPT_CONTEXT`,
  brand check is TypeId plus kind); and do not treat `-RecyclerStress`
  as a liveness result.
- The staging (`test/staging/sm/Iterator/**`) brand/other-realm
  tests could not be run: the qualified runner aborts on that
  harness. The equivalent behaviours are covered by the in-tree
  test (helper/generator cross-brand TypeErrors) and the
  cross-realm-tagged edition tests, which pass (2/0).
- Profiler registration covers the new prototype methods (labeled
  `Iterator`), the helper `next`/`return` functions (labeled
  `Iterator Helper`), the WrapForValidIterator `next`/`return`
  functions (labeled `WrapForValidIterator`), and both
  `Iterator.prototype` accessors (the `constructor` and
  `@@toStringTag` getter/setter pairs). The global constructor
  itself remains unregistered: `REG_GLOBAL_CONSTRUCTOR` keys on a
  static `PropertyIds::Iterator`, which does not exist by design
  (the global uses a tracked dynamic property id). This is inert
  in this fork because profiler registration is compiled only
  under `ENABLE_SCRIPT_PROFILING`, which no Zig profile defines.
  `%IteratorHelperPrototype%[@@toStringTag]` is installed with the
  helper prototype (the `ESIteratorHelpers` gate), not behind
  `ES6ToStringTag`. `Iterator.prototype`'s tag accessor uses that
  same gate. `Object.prototype.toString` reads `@@toStringTag`
  whenever the property is present.
- `Iterator.prototype[Symbol.dispose]` (explicit resource
  management) is post-ES2025 in the edition policy and deliberately
  absent; the edition-selected corpus does not require it.
