# C2-S4 — Optional chaining (`?.`) + logical assignment (`&&=` `||=` `??=`)

Batch receipt for S4 of [c1-triage.md](c1-triage.md), executed against
[plan milestone C2](modernization-plan.md). Implemented at HEAD `ed6e0994c`
(clean tree at start), Mac aarch64, no-JIT (`disable_jit` variant). No commit
was made by the implementing session; this file plus the source diff are the
deliverable.

## Verdict

Both features are implemented, **interpreter-verified**, and **enabled by
default** (`DEFAULT_CONFIG_ESOptionalChaining` /
`DEFAULT_CONFIG_ESLogicalAssignment` are `true`) on the evidence below.
Every remaining S4 test262 failure is attributed to a feature this batch
does not contain (class private elements, BigInt) or to a pre-existing
runtime ordering shared with plain member loads and compound assignment.
x64 JIT verification is **gated debt** (see "Limits" and "Round 3"): the
batch proves the interpreter configuration only, per project policy for
Mac sessions, and no JIT-configuration default or release claim follows
from this receipt.

### Remaining S4 failures (54), enumerated

- **42 — class private elements** (`class-fields-private`): every
  `left-hand-side-private-reference-*` scenario. Private names are not
  implemented anywhere in this engine; `#x` fails as `SyntaxError: Invalid
  character`, the same failure class as all other `#` syntax (plan C3 owns
  class elements). Per the batch scope, `a?.#x` likewise fails at the `#`.
- **6 — BigInt literals** (`lgcl-*-assignment-operator-bigint`):
  `ESBigInt` defaults off in this tree, so `1n` is a SyntaxError before
  logical assignment is reached. Other-feature failure, unchanged by S4.
- **6 — key-conversion ordering** (`lgcl-*-lhs-before-rhs`): for
  `base[prop] &&= …` with `base === null`, the engine converts the property
  key (throwing `toString`) before the null-base TypeError. Verified
  pre-existing: a plain load `base[prop]` and compound `base[prop] += 1`
  show the identical ordering on this tree. The other assertions in those
  files (evaluation counts, key-before-RHS) pass; the fix belongs to the
  shared element-load runtime, not to logical assignment emission.

## Design

No new bytecode opcodes, no new allocation domains, no GC or runtime-object
changes. Built-in bytecode verification confirms source headers unchanged.

**Scanner** (`Scan.cpp` `?`/`&`/`|` cases, gated on the new flags,
`ESNullishCoalescingOperator` precedent): `?.` is one token (`tkOptChain`)
only when not followed by a decimal digit, so `a?.5:3` stays a conditional;
`&&=`/`||=`/`??=` are single tokens mapping to new assignment node kinds at
assignment precedence (`kwd-lsc.h`), so `ParseExpr`'s existing
assignment-target validation, right-associativity, strict `eval`/`arguments`
checks, and the `??`/`&&`/`||` mixing error all apply unchanged.

**Optional chaining AST**: `ParsePostfixOperators` turns each `?.` segment
into one `knopOptChain` Tri node (appended at the end of `ptlist.h` so no
existing node values move): base expression, tail tree built over a
`knopTempRef` placeholder, and the `knopTemp` holding the base value in a
var register assigned by `AssignRegisters`. Bytecode emission evaluates the
base once, branches on `!= null` (the `knopCoalesce` pattern), and otherwise
emits the tail with all existing dot/index/call machinery — so `this`
binding, eval detection, spread, and super references in the tail reuse
proven paths. Two reference-sensitive cases get dedicated handling:

- `a.b?.()` (and nested forms like `a?.b?.()`, `(a?.b)?.()`): the member
  load runs once into callee/`this` temps (`EmitLoad`, or
  `EmitOptChainReference` for a parenthesized-chain base), and the tail call
  carries `ParseNodeCall::pnodeThisOverride`, emitted through `EmitCall`'s
  existing `overrideThisLocation`.
- Parenthesized chain as call target, `(a?.b)()`: `EmitCallTarget` emits
  the chain in reference mode (`EmitOptChainReference`), recovering the
  member base as `this`; a short-circuited chain yields an `undefined`
  callee that then throws at the call, per spec.
- `delete a?.b`: `EmitDeleteOptChain` returns `true` on short-circuit and
  otherwise deletes the tail member reference.

Early errors reuse existing machinery: a chain forces `fCanAssign = FALSE`
for its postfix invocation (assignment, update, for-in/of, and destructuring
targets all reject through the same checks as other invalid targets);
`new a?.b()` is rejected via a `pfHasOptChain` out-flag threaded through
`ParseTerm` (parenthesized `new (a?.b)()` stays valid); tagged templates
and `super?.x` error in the postfix loop. New node kinds were added to
every exhaustive consumer found by the `knopCoalesce`/`knopQmark` precedent:
`Visit`, `AssignRegisters`, `pnodewalk`, `CopyPnode`, tree printing,
side-effect/`arguments` analyses, and `Emit`.

**Logical assignment AST/emission**: `knopAsgLogAnd/LogOr/AsgCoalesce`
(Bin, `fnopAsg`, outside the compact compound range). Emission mirrors
compound assignment — `EmitBinaryReference` (extended with an `fEmitRhs`
parameter so the RHS stays behind the branch), `EmitLoad`,
`EmitAssignment`, `ReleaseLoad` — with `BrFalse_A`/`BrTrue_A`/`BrNeq_A`
guarding RHS evaluation and the store. Consequences that fall out of the
shared machinery and are covered by tests: base/key/getter evaluate once,
setter runs only when assigning, and a short-circuited assignment to a
`const` does not throw. One deliberate deviation from legacy operators:
a call/`new` LHS is an early `SyntaxError` for logical assignment even
though `f() = 1` / `f() += 1` are only runtime `ReferenceError`s under the
default `EarlyErrorOnAssignToCallPhase` setting. Logical assignment is new
syntax with no legacy content depending on that leniency, and test262
requires the early error (`lgcl-*-non-simple-lhs`). The check runs in both
AST and deferred (`!buildAST`) parses via a `pfIsCallResult` out-flag.
Round 2 threads that flag through `ParseExpr` and `ParseTerm`'s
parenthesized-expression case (the `pfCanAssign` sibling pattern), so the
parenthesized-call form `(f()) &&= 1` is also caught by a first deferred
pass; see "Round 2".

Alternatives rejected: (1) parser desugaring to `?:` over temp symbols —
cannot express `a.b?.()` once-evaluation plus `this` without inventing
symbol machinery, and mangles `delete`; (2) per-access optional node kinds
with sticky propagation — cannot distinguish "short-circuited" from a real
`null` intermediate (`a?.b.c` must throw when `a.b` is `null` but not when
`a` is), so whole-tail branching is required; (3) new bytecode opcodes —
unnecessary, since existing branch/load ops express every case and opcodes
would force bytecode regeneration and JIT lowering work.

## Limits / debt

- **JIT (x64 SimpleJIT/FullJIT) unverified — explicit gate.** This Mac
  session is interpreter-only. No new opcodes were introduced and all
  emitted patterns (`BrNeq_A`, `Ld_A/_ReuseLoc`, method loads,
  `DeleteFld/Elem`) predate the batch, so JIT lowering risk is low, but
  per plan C2 the JIT matrix still must pass under B4 before claiming JIT
  configurations. Round 3 considered JIT-scoping the defaults per function
  after the `JitES6Generators` precedent and decided against it (see
  "Round 3"): the defaults are global and carry Mac no-JIT evidence only.
  **B4 must run the S4 test262 corpus and the es7 tests under
  SimpleJIT/FullJIT (dynapogo) before any JIT-configuration default or
  release claim for these features.** Both features can be turned off with
  the `-ESOptionalChaining-` / `-ESLogicalAssignment-` config flags if a
  JIT issue appears (verified: the old SyntaxError behavior returns).
- Assign-to-call-result in the `!fEvaluateComponents` path
  (`(a?.b)() += 1`, runtime-error legacy path only) evaluates the chain in
  value mode, so its `this` differs from the reference-preserving path;
  the store still throws `ReferenceError` as for other call targets.
- Deferred-parse early errors: closed in round 2. `(f()) &&= 1` in a
  deferred function is now a first-pass `SyntaxError` (previously it
  surfaced only on reparse, tripping the "syntax errors should never be
  detected on deferred re-parse" assertion in debug builds). The earlier
  claim that a deferred first pass misses `super?.x` was wrong and did
  not reproduce: `ParseSuper` rejects the `?.` token in both parse modes,
  so it has always been caught upfront.
- `lgcl-*-lhs-before-rhs` (6 scenarios) needs the shared element-load
  key-ordering fix noted above; it is not S4-specific.

## Round 2 (review fixes, observed)

- **Critical — temp-register LIFO violation on member-target optional
  calls** (`a.b?.()`, `x[k]?.()`, `(a?.b)?.()`, `super.foo?.()`): debug
  builds asserted at `FuncInfo.cpp:380` (`tmpReg == curTmpReg - 1`). The
  `knopCall` `pnodeThisOverride` branch emitted the `this` temp, let
  `EmitCall`/`EmitCallI` acquire the call-result temp above it, then
  released the non-top `this` temp (release builds silently decremented
  the temp-stack pointer, freeing the live result slot). `EmitCall` never
  releases an override `this` (`releaseThisLocation == false`), so the
  caller owns it. Fix mirrors the only other override caller,
  `EmitSuperCall`: pre-acquire the call result slot below the `this` temp
  (when the result is used), so the callee temp is released inside
  `EmitCallI`, the result reuses its pre-acquired slot, and releasing
  `this` after the call is top-of-stack; the result slot stays acquired
  for the consuming parent, as for any other call. Verified on
  `out/debug-static/bin/ch`: the minimal repro prints `42`; the four
  previously asserting test262 scenarios
  (`optional-call-preserves-this` ×2, `super-property-optional-call` ×2)
  pass 4/4; S4 scoped repro unchanged at 154/54
  (`out/test262-s4r2-optchain`). Amended by round 3: this fixed the LIFO
  shape family (single member-target optional calls), but the nested
  call form (`o.m?.().g?.()`) was still broken — a different register
  defect in the same temps — and is fixed there; read the round-2 claim
  as scoped to the shapes listed here.
- **Deferred `(f()) &&= 1`**: now a first-pass `SyntaxError` under both
  `-forcedeferparse` and `-nodeferparse` on debug and test binaries (no
  abort, no generic internal error); legacy `(f()) = 1` / `(f()) += 1`
  remain runtime errors only, unchanged.
- **Registration + gates**: both es7 tests registered; observed totals
  1961/0 (test) and 2013/0 (debug) from full `runtests.py` runs before
  any expectation was edited; `mise x -- zig build check` passes at
  1961/0 and the full `--debug` run passes at 2013/0 on the debug binary.
- **Trigraphs**: the two new `"??="` literals in `Parse.cpp` are escaped
  as `"?\?="` (as the `ptlist.h` node table already does); clang
  `-Wtrigraphs` is silent and the string value is unchanged.

## Round 3 (external review fixes, observed)

- **Critical — nested member optional call crashed emission**
  (`o.m?.().g?.()` and family): opening the second `?.()` segment does
  not close the first, so the first call — with its `pnodeThisOverride`
  temp — lands in the second segment's base. The twin spine walks that
  find a segment's `this` temp (`GetOptChainThisTemp`,
  `ByteCodeGenerator.cpp:4837`, register assignment;
  `GetOptChainThisTempNode`, `ByteCodeEmitter.cpp:7431`, base emission)
  stopped at a nested `knopOptChain` tail, so the temp never got a
  register (debug "bad register" assert, release abort) and would not
  have been filled even with one. Both walks now descend into a nested
  segment's base and take the first override on the extended spine,
  which is the segment's own (opening a value form closes any open
  call-form segment first, so no foreign override sits below a
  value-form spine); cross-reference comments pin the twins together.
  Override temps off the spine (arguments, index keys) belong to their
  own `knopOptChain` nodes, which `Visit`/`AssignRegisters` already
  reach independently. Verifying the fix exposed a second latent defect
  in the same family: `EmitOptChainReference` registered an LdFld
  call-cache id for its tail register, but the value is copied out of
  that register before any call, so the writer-map entry went stale and
  a second parenthesized-chain call (`(a?.b)?.()` twice) asserted at
  `ByteCodeWriter.cpp:2143`; it now passes
  `registerCacheIdForCall=false` (`ByteCodeEmitter.cpp:7551`), matching
  the one other caller whose load does not feed a call in-register.
  New cases in `test/es7/optionalchaining.js` pin the family: nested
  dot/index forms, three levels, plain call in the middle,
  argument-nested member optional calls, per-segment short-circuit,
  repeated parenthesized calls, `super.m?.()` / `super.x?.().y?.()`,
  and `o[k]?.()`; `(o.m?.()).g?.()` remains as the working control.
- **Critical — function values through `??`/`??=` escaped unsoundly**:
  `AssignRegisters`' `knopCoalesce`/`knopAsgCoalesce` case
  (`ByteCodeGenerator.cpp:5076`) assigned the null constant but skipped
  the `CheckMaybeEscapedUse` child walk every other binary operator
  gets from the default case, so `y ?? function(){}` /
  `y ??= function(){}` could stack-allocate a nested function that is
  then returned (debug assert at `InterpreterStackFrame.cpp:7928`,
  release crash). Both forms now walk both children, exactly as
  `&&=`/`||=` do via the default case. **The plain-`??` half is a
  pre-existing memory-safety bug, not an S4 regression**: the same
  repro asserts identically on the pre-S4 legacy binary
  (`build-legacy-debug/bin/ch/ch`), while `||`, `&&`, and `?:` controls
  pass there; fixing it here is deliberate and in scope. Investigated
  and rejected adding `CheckFuncAssignment` for `??=`: that is plain
  `=`'s stack-nested-func optimization for an unconditional store —
  `&&=`/`||=` do not get it either and are correct via the conservative
  escaped marking, and `EmitAssignment`'s shared store path (already
  used by logical assignment) handles slot commitment at emit time, so
  no `SetIsCommittedToSlot` handling is missing. Regression cases
  (returned closures via `??=`, `??`, capture, arrow, plus
  `&&=`/`||=`/`=` controls) are in `test/es7/logicalassignment.js`;
  the plain-`??` cases live there rather than in `nullish.js` so the
  operator family stays in one file, as their comment records.
- **`??=` flag gating**: scanning `??=` required only
  `ESLogicalAssignment`, so it worked with
  `-ESNullishCoalescingOperator-` while `??` was a `SyntaxError`. It now
  requires both flags (`Scan.cpp:1783`), mirroring how `??` scans;
  `-ESLogicalAssignment-` still kills all three assignment forms and
  leaves plain `??`. Verified by the full 4×4 flag/file matrix on the
  test binary in this round (each disabled form is a `SyntaxError`,
  each enabled form evaluates).
- **Default-on vs plan C2's JIT clause — decision: document, do not
  JIT-scope.** `JitES6Generators` (`ConfigFlagsList.h:1228`) works
  because "is a generator" is an intrinsic `FunctionInfo` property the
  JIT entry path already consults (`FunctionBody.cpp:351`); generators
  needed it because they emit coroutine bytecode the JIT could not
  lower. S4 has no equivalent hook: whether a function uses `?.` or
  logical assignment is not recorded anywhere, and every opcode S4
  emits pre-dates the batch, so there is no lowering gap for a
  per-function bit to guard. Adding one would mean new
  parser→`FunctionBody`-flag plumbing (with deferred-parse and
  serialization surface) invented and left untestable on this no-JIT
  host — more risk than the policy it encodes. Instead the gate is
  explicit in "Limits" above and in the plan's C2 record: defaults are
  global, evidence is Mac no-JIT only, and B4 must run the S4 corpus
  and es7 tests under SimpleJIT/FullJIT (dynapogo) before any
  JIT-configuration default or release claim; kill switches are
  `-ESOptionalChaining-` / `-ESLogicalAssignment-`. Commit-facing
  wording now says "interpreter-verified" (verdict above,
  `doc/c1-triage.md`, `doc/modernization-plan.md`).
- **Tests/docs hygiene**: `logicalassignment.js` is now registered with
  `-forcedeferparse` (mirroring `asyncawait-syntax.js` neighbors) with
  an in-file deferred-parse case, pinning the round-2 first-pass error
  in the registered gate; all new cases are inside the two existing
  files, so registered totals held (below). Live count references
  updated to 1961 (`tools/test262/README.md`,
  `doc/memory-management.md` — its `ChakraCore.h:1959-1995` line range
  untouched; historical B2/B3 records keep their counts), the
  `check_regression.py` count citation now points at this receipt, and
  the evidence table's before/after outputs are corrected above.

  C1 shape print `5` (plus stress suites for nesting depth, argument
  and index-key temps, getters-once, statement/return/array/async
