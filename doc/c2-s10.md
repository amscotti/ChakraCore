# C2-S10: copy-by-change (half)

Status: closed. The copy-by-change half is implemented and
interpreter-verified on Mac no-JIT. The Set-methods half is now landed
too — see "Set methods (rest of S10)" below; this section covers the
array and typed-array methods only.
No feature flag and no kill switch. JIT evidence is not claimed; see
B4 below.

## Supported configuration

- Default Mac profiles (test and debug-static gates): the seven methods
  are present. There is no `ConfigFlagsList` entry for them.
- No kill switch. Removing a method would be a library change, not a
  flag. Precedent: `String.prototype.replaceAll`.
- `ESBigInt` is off. Typed-array `with` uses `ToNumber`, not `ToBigInt`.

## What landed

Unconditional library methods. No new opcode, no bytecode constant, no
Backend helper, no new `TypeId`, no static `PropertyIds` entry, and no
`builtinFuncs[]` slot. `JavascriptBuiltInFunctionList.h` registers
`BUILTIN(..., FunctionInfo::ErrorOnNew)` for each entry. That is the
runtime entry id (`new` throws). It is not an opcode.

`Array.prototype`:

| Method | Length | Entry |
| --- | --- | --- |
| `toReversed` | 0 | `JavascriptArray::EntryToReversed` |
| `toSorted` | 1 | `JavascriptArray::EntryToSorted` |
| `toSpliced` | 2 | `JavascriptArray::EntryToSpliced` |
| `with` | 2 | `JavascriptArray::EntryWith` |

`%TypedArray%.prototype` (no `toSpliced`):

| Method | Length | Entry |
| --- | --- | --- |
| `toReversed` | 0 | `TypedArrayBase::EntryToReversed` |
| `toSorted` | 1 | `TypedArrayBase::EntryToSorted` |
| `with` | 2 | `TypedArrayBase::EntryWith` |

Install uses `AddFunctionToLibraryObjectWithPropertyName` (tracked
dynamic property id). `InitializeArrayPrototype` passes `31` to
`DynamicTypeHandler::Convert` as a capacity hint, not an own-property
count. `InitializeTypedArrayPrototype` passes `34`. Array
`@@unscopables` sets `toReversed`, `toSorted`, and `toSpliced` to
true via `GetOrAddPropertyIdTracked`. `with` is omitted: it is a
keyword and cannot be an identifier
(`sec-array.prototype-@@unscopables`). The typed-array prototype has
no `@@unscopables` entries for these. Profiler registration uses
`REG_OBJECTS_DYNAMIC_LIB_FUNC` (character counts 10, 8, 10, 4 on arrays;
10, 8, 4 on typed arrays). No `CHAKRATEL` id was added.

Array results are `JavascriptLibrary::CreateArray`. That is `ArrayCreate`.
The methods do not read `.constructor` or `@@species` and do not call
`ArraySpeciesCreate`. Typed-array results are
`TypedArrayBase::CreateSameType`: `CreateArrayBuffer(byteLength)` then a
`TypeId` switch to that type's static `Create` (`Int8` through `Bool`,
the TypeIds `ValidateTypedArray` can return). An unknown TypeId is
`AssertMsg` plus `FatalInternalError`. `CreateSameType` does not call
the JS constructor and does not call `TypedArrayCreate`. A byte length
past `ArrayBuffer::MaxArrayBufferLength`, or a multiply overflow, throws
`RangeError` (`JSERR_InvalidTypedArrayLength`). Length 0 is a new empty
array of the same type, not the receiver.

`toSorted` does not invent a sort. The array path materializes every
index onto the new dense array, then calls the existing
`JavascriptArray::SortHelper` on that copy only (`StringItem` /
`stringCompare` when `comparefn` is undefined; `Field(Var)` when a
callable is present). The typed-array path copies into the new buffer,
then calls the virtual `TypedArrayBase::SortHelper` on that buffer only.
A null `comparefn` there is numeric (`x < y`), not string compare.
Neither path calls `SortHelper` or `EntrySort` on the receiver, and
neither copies the sorted bytes back.

A non-callable, non-undefined `comparefn` throws `TypeError`
(`JSERR_FunctionArgument_NeedFunction`) before `ToObject` /
`ValidateTypedArray` and before any length get.

`toSpliced` does not call `EntrySplice`. A present `undefined`
`deleteCount` is `ToInteger` 0 (a copy at that start). A missing
`deleteCount` deletes through the end. `toSpliced()` with only `this`
is a full copy.

Array `with` stores the provided value with no `ToNumber`. Typed-array
`with` does `ToIntegerOrInfinity(index)`, computes the actual index from
the captured length, then always `ToNumber(value)`. A throw from that
value propagates, including when the index is out of range or the buffer
was detached during `ToInteger`. After `ToNumber`, a buffer that is now
detached or an out-of-range index is `RangeError`
(`JSERR_InvalidTypedArrayIndex`), before `CreateSameType`. The copy does
not run for those cases, so a detach during `ToNumber` is not left to
`DirectGetItem`.

## Limits

These are platform or pre-existing gaps. They are not open defects in
the seven methods.

- `toSpliced` length limit. The spec throws `TypeError` when
  `newLen > 2^53-1` and `RangeError` from `ArrayCreate` when
  `2^32-1 < newLen <= 2^53-1`. This engine's arrays are `uint32`, so
  both checks are implemented: `TypeError`
  (`JSERR_IllegalArraySizeAndLength`) above `2^53-1`, then
  `RangeError` (`JSERR_ArrayLengthConstructIncorrect`) above
  `UINT32_MAX`. A `newLen` of `2^32` is `RangeError`, not `TypeError`.
  Existing `splice` overflow is a different `RangeError`
  (`JSERR_ArrayLengthAssignIncorrect`). Both throws happen before any
  element `Get` and before allocation of that length.
- A source length above `UINT32_MAX` is legal when `newLen` fits.
  `ToLength` clamps at `2^53-1`. Tail gets use `GetItem` on `uint64`.
- `ESBigInt` is off. A source file that contains `42n` or `1n` fails to
  parse (`SyntaxError: Unexpected identifier after numeric literal`)
  before the method runs. `analyze.py` calls the untagged files
  `engine-defect-on-existing` and the `BigInt`-tagged files
  `disabled-flag`. The cause is the parse error.
- Resizable `ArrayBuffer` is S8 and is not implemented.
  `ArrayBuffer.prototype.resize` throws `TypeError: Object doesn't
  support property or method 'resize'`. Typed-array `with` tests that
  resize during `ToNumber` or during index coercion fail for that
  reason. Four scenarios expect a `RangeError` after a successful
  resize and instead see that `TypeError`. `analyze.py` buckets the
  direct `resize` throws as `required-feature-missing` and those four
  as `engine-defect-on-existing`. The cause is the missing `resize`.
- Typed-array default numeric compare
  (`TypedArrayCompareElementsHelper`, also `TypedArray.prototype.sort`)
  uses `x < y`. `-0` and `+0` compare equal, so a stable sort of
  `Float64Array([0, -0])` stays `[0, -0]`. The spec's default
  `CompareTypedArrayElements` orders `-0` before `+0` (`x` is `+0` and
  `y` is `-0` returns `+1`; the reverse returns `-1`). That rule
  applies only when `comparefn` is absent. Integers have no `-0`. The
  predicate was left unchanged because the helper is shared with the
  shipped `sort`.
- Detach window after `CreateSameType`. `toSorted` re-checks
  `IsDetachedBuffer` after `CreateArrayBuffer`, because finalizers can
  detach, and throws `TypeError` (`JSERR_DetachedTypedArray`) before
  `memcpy`. `toReversed` and `with` do not re-check after create. A
  detach during that allocation can still `TypeError` later from
  `DirectGetItem`. Align the three methods before S8.
- S8 landmines, latent while `resize` is absent. `with` validates the
  index against the length captured before `ToNumber`. The spec checks
  the current length after the coercions. `toSorted`'s `memcpy` uses
  the captured `length * elementSize` after the detach re-check. A
  future shrink below that byte length would read past the buffer.
- Typed-array `with` hard-codes `ToNumber`. The spec uses `ToBigInt`
  for bigint element types. Latent until `ESBigInt` (S2). There is no
  `ToBigInt` path while that flag is off.
- A legal `toSpliced` whose `newLen` is `2^32-1` copies about four
  billion elements. The spec allows it. The implementation runs that
  loop. It is a resource bound.
- `toSpliced`'s `TypeError` above `2^53-1` uses
  `JSERR_IllegalArraySizeAndLength`. That resource has an empty format
  string and no method name, and other callers share it. The thrown
  type is `TypeError`. The message was left unchanged.
- No typed-array `toSpliced`. Set methods are unstarted. `matchAll`
  stays behind S7. Named groups are not part of this batch.
- `JavascriptArray::SortHelper` still skips holes and pulls `undefined`
  out of the comparison. `toSorted` matches the spec only because every
  index was already written as an own data property, including
  `undefined`. `Array.prototype.sort` still mutates and keeps holes.
- `EntrySort`'s `BEGIN_TEMP_ALLOCATOR` still has no `END` on the throw
  path. That function was not changed.

## Ownership

Array results and typed-array `ArrayBuffer`s are recycler objects
(`CreateArray`, `CreateArrayBuffer`, `CreateSameType`). No write-barrier
change. No `-RecyclerStress` run.

The only new non-GC allocation is the typed-array `toSorted` scratch
arena (`TypedArray.cpp`, stack `SortScratch`, used only when
`length >= 2`).

```text
Resource / creation call / source location:
  Temp arena for TypedArrayBase::SortHelper mergesort.
  ScriptContext::GetTemporaryAllocator("toSorted") inside SortScratch.
Domain and allocator instance (including backing allocator lifetime):
  ScriptContext / ThreadContext temporary allocator pool
  (MaxTemporaryArenaAllocators). Not a GC object.
Physical allocation base, extent, alignment, release callback or pool kind:
  ArenaAllocator from the temp pool. SortHelper AnewArrays on it when
  length >= 512. ReleaseTemporaryAllocator returns the pool slot.
Logical length / borrowed views (kept separate from the allocation descriptor):
  Sort scratch only. The typed array's bytes stay in the new recycler
  ArrayBuffer. The source buffer is not aliased by the arena.
Owner; transfer/publication point; remaining aliases:
  Stack SortScratch. Copy and assignment are deleted. SortHelper borrows
  the arena for the call and does not retain it.
Borrow invalidation: GC / detach / growth / mutation / reset / close / disposal:
  Destructor releases the arena on success and on unwind, including a
  throw from comparefn. The new typed array does not borrow the arena.
Potential user-code or reentrancy points:
  comparefn. Each nested toSorted takes its own allocator. The source
  byte buffer is not held across comparefn; the values were already
  copied. A detach of the source during comparefn does not throw and
  does not write the source.
Thread/context allowed for use, root changes and destruction:
  The calling script context only.
Release on success, partial failure, exception, OOM, cancel and shutdown:
  SortScratch destructor. Length < 2 does not take an allocator.
Memory accounting, capacity/retention bound and exhaustion behavior:
  One pool slot per in-flight toSorted. Not retained past the call.
  Pool exhaustion uses the existing temporary-allocator failure path.
Tests / commands / measured results / remaining uncertainty:
  In-tree stable compare and numeric default sort. test262 toSorted
  comparefn cases that parse. Not claimed: OOM injection,
  -RecyclerStress, or a JIT allocation profile.
```

Array `toSorted` calls the existing `JavascriptArray::SortHelper`, which
already takes `BEGIN_TEMP_ALLOCATOR` and `END_TEMP_ALLOCATOR` on the
success path only. That leak-on-throw is pre-existing (`EntrySort` has
the same shape). This batch did not add a second array arena.

### Design notes

`GetSetRecord` is a file-local `SetLikeRecord` in `JavascriptSet.cpp`
built in the spec's observable order: the Object check (`TypeError`),
Get `size`, `ToNumber`, the NaN `TypeError`, `ToIntegerOrInfinity` of
the already-converted number, the negative `RangeError`, Get `has`
with its callable check, then Get `keys` with its callable check. A
size of `Infinity` is accepted. The NaN `TypeError` and negative
`RangeError` use `JSERR_FunctionArgument_Invalid` with the method
name; the callable checks use `JSERR_FunctionArgument_NeedFunction`.
`ToNumber` runs exactly once (a `valueOf` is not re-entered by the
truncation, which is `JavascriptConversion::ToInteger(double)`).

The receiver is read through its internal set data only — `Size`,
`Has`, `Add`, `Delete`, and the live `SetDataList` iterator. No
user-visible `add`, `has`, `size`, or `keys` is called on the
receiver, and result sets are fresh `library->CreateSet()` objects:
no `.constructor`, no `@@species`, `Object.getPrototypeOf(result) ===
Set.prototype`. The other record's `[[Has]]` and `[[Keys]]` ARE user
code and run under `JS_REENTRANCY_LOCK`/`JS_REENTRANT` regions; the
iterator protocol is `CacheIteratorNext` (Get `next` once, callable
check) plus `IteratorStepAndValue` (call `next`, require an Object
result, Get `done`, then Get `value`).

Walk selection follows the sizes: `difference`, `intersection`, and
`isDisjointFrom` walk the receiver and call `other.has` when
`thisSize <= otherSize`, and iterate `other.keys` checking the
receiver's internal `Has` otherwise. `isSubsetOf` returns false
immediately when `thisSize > otherSize` (no `has` call); `isSupersetOf`
returns false immediately when `thisSize < otherSize` (no iteration).
`union` and `symmetricDifference` always iterate `other.keys` and
never call `other.has`. `union` and `symmetricDifference` create the
keys iterator BEFORE copying the receiver; `difference` copies first.

Mutation semantics follow the ES2025 algorithms exactly, verified
against the corpus mutation tests and Node 26:

- The receiver copy (`CopySetData`) is taken after `GetSetRecord`
  completes (and after the `keys()` call for `union` and
  `symmetricDifference`), so a `has`/`keys` getter that mutates the
  receiver is included in the copy.
- The `has` walks of `intersection`, `isSubsetOf`, and `isDisjointFrom`
  iterate the receiver's LIVE list: entries deleted by `has` are not
  visited, re-added and newly added entries are visited (the
  `SetDataList` iterator's documented semantics), and `intersection`
  dedupes re-visited entries against the result.
- `difference`'s has walk iterates its own private COPY (the result
  set): a fixed-extent walk. Entries `has` deletes from the receiver
  are still passed to `has`, and entries `has` adds are not visited.
- The keys walks check membership against the LIVE receiver for
  `intersection`, `symmetricDifference`, `isSupersetOf`, and
  `isDisjointFrom`, but against the copy for `difference` — each
  method per its algorithm. `symmetricDifference` removes a value
  from the copy only when the live receiver still contains it, and
  appends only when neither the live receiver nor the copy has it.
- Values taken from the record's iterator are canonicalized `-0` to
  `+0` (`CanonicalizeSetMethodKey`, mirroring `EntryAdd`) before any
  `Has`/`Add`/`Delete` on a result. The `is*` walks do not
  canonicalize; they only test membership, and SameValueZero already
  equates `-0` and `+0`.
- Early exits of `isSupersetOf` and `isDisjointFrom` close the keys
  iterator; natural exhaustion does not, matching
  `set-like-iter-return.js`. Review found and fixed a spec deviation
  here: these two exits are NORMAL completions, so the close itself
  runs the full spec steps — GetMethod `"return"` with propagation
  (undefined/null → nothing, non-callable → `TypeError`), Call with
  propagation, and a `TypeError` when the call result is not an
  Object. The file-local `CloseKeysIteratorNormalCompletion`
  (`JavascriptSet.cpp`) implements this and is used at exactly those
  two early-exit sites; tests mirror Node 26 for a throwing
  `return()`, a non-object `return()` result, a throwing `"return"`
  getter, a non-callable `"return"`, and the absent-`"return"`
  early false. The shared `JavascriptOperators::IteratorClose`
  retains its legacy swallow semantics for its pre-existing callers
  (they reach it on abrupt completions, where the spec also drops
  the inner error); recording that engine-wide behavior is out of
  this batch's scope.

## Limits (Set methods)

These are platform or pre-existing gaps. They are not open defects in
the seven methods.

- `ESBigInt` is off. The 21 corpus files that contain a BigInt literal
  (`size-is-a-number.js`, `require-internal-slot.js`,
  `called-with-object.js` for each method) fail to parse with
  `SyntaxError: Unexpected identifier after numeric literal` before
  any method runs — 42 of 372 scenarios. `analyze.py` buckets them
  `required-feature-missing`.
- Error message texts differ from Node (`Object expected` versus
  `Result of the keys method is not an object`, `Function expected`
  versus `string "next" is not a function`). The error TYPES match;
  the corpus checks types only.
- `GetSetRecord`'s negative-size `RangeError` and NaN `TypeError` use
  `JSERR_FunctionArgument_Invalid`, whose format string carries the
  method name. No corpus test pins the text.
- `Set.prototype` gained seven enumerable-in-name-only functions and
  `indexprop.js.dbg.baseline` lists them (see Test). No other
  debugger snapshot dumps `Set.prototype`.

## Ownership (Set methods)

No new allocation domain. Result sets are recycler objects
(`CreateSet`), and every intermediate is either a stack
`SetLikeRecord`/`SetLikeKeysIterator` of recycler pointers or the
receiver's own data. No write-barrier change, no temp arena, and no
non-GC allocation. Not claimed: OOM injection, `-RecyclerStress`, or
a JIT allocation profile.
